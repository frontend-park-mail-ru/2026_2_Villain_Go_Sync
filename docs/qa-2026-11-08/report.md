# Проверка фронтенда HireNoon — 8 ноября 2026

Проверено состояние `fix/rk2-validation`, коммит `4edc8b8`.
Бэкенд: `fix/api-consistency`, коммит `3eb1fd5`, запущенный отдельно от рабочей папки.
Проверка ограничена существующим интерфейсом. Категории, PDF, уведомления и избранное не добавлялись.

## Результат

Основные сценарии работают. Граничные случаи выявили дефекты отображения, потери введённых данных,
обработки сетевых ошибок и валидации. Изменения в код приложения не вносились.

Приоритет P2 — исправить до демонстрации соответствующего сценария. P3 — менее существенная ошибка
или улучшение. Среди перечисленного нет подтверждённого обхода авторизации или выполнения
переданного в поля JavaScript; это не заключение о безопасности всего приложения.

## Условия и покрытие

- Chromium, Windows. Проверка реального CORS: фронт `localhost:8000`, API `localhost:8080`.
- Отдельная тестовая БД и MinIO проекта Docker `hirenoon-rk2`; рабочая БД не использовалась.
- Линтер, проверка типов и production-сборка прошли. Существующие 21 Playwright-тест прошли.
- Дополнительно исследованы более 200 сценариев/граничных вариантов, включая повторные подтверждения.
- Размеры экрана: 320, 375, 768, 1024, 1440 px; длинные строки без пробелов и текст с HTML-символами.
- С подставными ответами API: 0, 1, 12, 13, 25, 1000, 10000 объектов каждого из четырёх списков;
  пустые результаты, поиск, сброс, первая/последняя/предыдущая страницы, 500 и отсутствие сети.
- С настоящим API: создана 61 вакансия, 37 резюме, 25 откликов; проверены последние страницы списков.
- Валидация: почта, роль, пароль 7/8/72/73 символа, регистры/цифры/символы;
  имя и компания; телефон 9/10/15/16 цифр; сайт; суммы/диапазон зарплаты;
  пустые и невидимые названия; изображения 0 байт и более 10 МиБ; большое письмо отклика.
- Сессия: cookies, реальный CSRF, неверная роль, refresh при 401, отказ refresh,
  общий refresh параллельных запросов, новая вкладка, перезагрузка, выход.
- Состояния форм: повторная отправка, отмена, переход во время загрузки, ошибка сохранения,
  наличие профиля, восстановление черновика. Запрет редактирования чужих записей проверен в UI с fixtures.
- Production-сборка: service worker, офлайн-загрузка оболочки и кэшированной ленты;
  в проверенном свежем кэше нет `/me`, профилей или резюме.
- Базовые проверки доступности: подписи полей, `aria-invalid`, кнопка пароля, поведение диалога.
  Полноценного аудита скринридером не было.
- Firefox скачан, но запуск завершился инфраструктурной ошибкой `browserType.launch: spawn UNKNOWN`.
  Совместимость с Firefox, Safari/WebKit и реальными мобильными устройствами не подтверждена.
- Испытание 10000 объектов проверяет клиентское отображение подставного ответа, а не пропускную способность API.

## Дефекты и решения, требующие согласования

### QA-01 · P2 · Искажение обычного текста при сохранении — реальный API

1. Войти соискателем, открыть `/resumes/new`.
2. Ввести название `R&D`, создать резюме.
3. Посмотреть заголовок записи.

Ожидание: `R&D`. Факт: `R&amp;D`, включая заголовок и хлебные крошки.
Результат подтверждён реальным браузером; [снимок](real-text-encoding.png).

Причина находится на границе API и шаблонизатора: серверный `SafeString` использует
`bluemonday.StrictPolicy().Sanitize`, а Handlebars экранирует полученную строку при выводе.
Нужно согласовать текстовый JSON-контракт с бэком. Не исправлять отключением экранирования
или вставкой пользовательского текста через `innerHTML`.
Фронт: `src/pages/ResumePage.hbs`, `src/pages/ResumeFormPage.ts`.

### QA-02 · P2 · Потеря несохранённой формы при обычной навигации — fixtures

1. Открыть `/resumes/new`, `/vacancies/new` или `/profile/edit` под подходящей ролью.
2. Изменить поле.
3. Нажать логотип/ссылку шапки.

Факт: переход без подтверждения, введённый текст теряется. Через кнопку «Отмена» подтверждение есть.
Черновик сохраняется только в специальном сценарии отсутствующего профиля, а не при обычном уходе.
Нужна единая проверка несохранённых изменений для переходов; правила для Back/Forward и закрытия
вкладки также следует определить.
Код: `src/router.ts:171`, `src/pages/ResumeFormPage.ts:223`,
`src/pages/VacancyFormPage.ts:275`, `src/pages/ProfileFormPage.ts:175`.

### QA-03 · P2 · Кнопка отклика выходит за экран 320 px — fixtures

1. Войти соискателем, открыть чужую вакансию с короткими обычными данными.
2. Установить ширину окна 320 px.

Факт: ширина документа 376 px, правая граница кнопки — 376 px; появляется горизонтальная прокрутка.
[Снимок](short-vacancy-320.png). Ошибка не требует длинного названия компании.
В заголовке не помещаются название, зазор 32 px и кнопка фиксированной ширины 176 px.
Код: `src/styles/detail.scss:14`, `src/styles/detail.scss:46`.

### QA-04 · P2 · Длинное название компании ломает страницу вакансии — fixtures и реальный API

1. Сохранить название компании без пробелов примерно в 150–200 символов.
2. Открыть её вакансию.

Факт: название компании в `.detail__subtitle` не переносится и раздвигает страницу.
На реальном API окно 320 px получило документ шириной 1987 px.
На синтетическом тексте проблема воспроизведена при всех пяти проверенных ширинах.
Нужны ограничение ширины flex-элемента и перенос/усечение длинного текста.
Код: `src/pages/VacancyPage.hbs:67`, `src/styles/detail.scss:107`.

### QA-05 · P2 · Несогласованное значение зарплаты 0 — реальный API

Форма допускает 0, сервер сохраняет 0. При `salary_from=0` и `salary_to=0` детали и карточки
пишут «Зарплата не указана», хотя числовое значение было введено.
Нужно выбрать одно поведение: отображать ноль, запрещать его как неподходящую зарплату
или явно преобразовывать его в отсутствие значения. Сейчас форма и представление расходятся.
Код: `src/format.ts:18`, `src/pages/VacancyPage.ts:117`, `src/pages/VacanciesPage.ts:139`.

### QA-06 · P2 · Большое письмо отклика не проверяется на фронте — реальный API

1. Открыть окно отклика, выбрать резюме.
2. Вставить 40000 кириллических символов и отправить.

Факт: запрос отправляется, сервер его отклоняет, показана общая ошибка отправки.
Сервер ограничивает JSON-тело 64 КиБ; frontend не учитывает этот предел.
Нужно определить понятный лимит письма с бэком и проверять его в JS до отправки,
учитывая байтовый размер/UTF-8 и остальные поля запроса. Не называть текущую общую ошибку
сетевым сбоем: в этом случае нужно сократить ввод.
Код: `src/components/ApplicationDialog.hbs:34`, `src/components/ApplicationDialog.ts:67`.

### QA-07 · P2 · Невалидные адреса почты проходят регистрацию — fixtures и реальный API

Примеры: `.qa@example.com`, `qa..name@example.com`, `qa@-example.com`.
Фронт отправляет такие значения. Адрес с ведущей точкой реально зарегистрирован сервером с 201.
Это общая проблема валидации на обеих сторонах, а не несовпадение текущих regex.
Нужны согласованные проверки локальной части и доменных меток; на бэке должна сохраниться
независимая валидация независимо от фронта.
Код: `src/validation.ts:2` и серверный `internal/delivery/auth/validation.go`.

### QA-08 · P2 · Временный сбой `/me` выглядит как выход из аккаунта — fixtures

При существующих cookies заменить ответ `/me` на 500 или сетевую ошибку и открыть `/profile`.
Факт: пользователь перенаправлен на `/login`, вместо сообщения о сбое проверки сессии и повтора.
Серверные cookies при этом не удалены; речь о состоянии интерфейса, а не уничтожении сессии на сервере.
`restoreSession()` трактует любую ошибку как отсутствие сессии.
Код: `src/api.ts:405`.

### QA-09 · P3 · Ошибка ушедшей регистрации появляется на другой странице — fixtures

Задержать `/register`, отправить валидную форму, перейти по логотипу на главную;
позже вернуть 500 регистрации. На главной появляется чужое уведомление ошибки.
В `catch` нет проверки `#isDestroyed`, хотя проверка перед успешным переходом есть.
Код: `src/pages/RegisterPage.ts:96`. Аналогичный участок входа следует проверить при исправлении.

### QA-10 · P3 · Подпись переключателя пароля не соответствует действию — fixtures

После показа пароля `type=text` и `aria-pressed=true`, но `aria-label` остаётся «Показать пароль».
Ожидается «Скрыть пароль». Это дефект доступности, само переключение работает.
Код: `src/components/form.ts:51`.

## Дополнительные улучшения, не блокирующие обычный сценарий РК2

- Поле сайта принимает `https://example..com`; проверки наличия точки в hostname недостаточно.
  Адрес с userinfo `https://example.com@evil.test` также принимается. Это синтаксически допустимый URL,
  поэтому требование запрещать userinfo нужно явно согласовать; сам по себе этот результат не доказывает уязвимость.
- Названия из одних U+200B принимаются: визуально запись может оказаться без названия.
  Нужна договорённость о фильтрации невидимых символов.
- Неизвестный статус отклика отображается как «Новый», а не как неизвестный статус.
  Проверено только на искусственном `future_status`, текущий сервер такой статус не отдавал.
- Ввод зарплаты `10 0` интерпретируется как 100. Код специально удаляет пробелы;
  без требования к группировке разрядов это особенность текущего поведения, а не доказанный дефект.
- Поиск на главной обещает компанию в placeholder, но текущий фильтр ищет в названии/описании.
  Полноценный поиск относится к РК3: для РК2 достаточно согласовать честную подпись поля,
  не расширяя продуктовый объём.

## Что прошло без выявленных ошибок в проверенных случаях

- Регистрация/вход корректными данными и различение ролей.
- HttpOnly access/refresh cookies, читаемая CSRF-cookie, передача заголовка и CORS.
- Отказ неверной роли на настоящем сервере; запрет создания форм другой роли и редактирования чужих записей в UI.
- Общий refresh одновременных запросов, отказ refresh и перевод на вход, новая вкладка, выход.
- Массовые списки, пагинация, поиск по реализованным полям, сброс и retry после ошибки сети/500.
- Для 10000 подставных объектов проверенный сценарий открытия и переходов укладывался примерно в 214–283 мс
  на этой машине. Это единичное локальное измерение, не нагрузочный бенчмарк сервера.
- Отправка отклика с одним/многими резюме, обязательность выбора, список из 100 резюме.
- Сохранность полей после ошибки сохранения; защита от тройной отправки формы во время ожидающего запроса.
- Валидация основных границ пароля, телефона, отрицательных/дробных/слишком больших зарплат и обратного диапазона.
- Изображения: пустой файл, неверный MIME, превышение 10 МиБ, ошибка загрузки без потери текстовых полей.
- Безопасный вывод проверенных HTML/XSS-строк в fixtures: код не исполнился.
- Некорректные ID и битая URL-кодировка показывают not-found; диалог закрывается при навигации без удаления.
- Офлайн-оболочка production-сборки и кэш общей ленты при отсутствии сети.
